Labtris is server software. It runs on a Linux machine, boots your containers
and virtual machines there, and everyone else reaches it with a browser. Nothing
is installed on the machines people use it from.

## What it needs

| | |
|---|---|
| **CPU** | x86-64. Virtualisation extensions if you want QEMU nodes to run at useful speed |
| **RAM** | 8 GB is a comfortable floor. Each QEMU guest wants what its image wants; containers want almost nothing |
| **Disk** | 40 GB plus whatever your images take. A desktop OS image is 2–6 GB |
| **OS** | Ubuntu 24.04 or 26.04 for the one-line installer and the ISO. Any Linux with Docker for the container install |

Labtris will run without hardware virtualisation — QEMU falls back to software
emulation — but a guest that boots in twelve seconds with KVM can take four
minutes without it.

## Ubuntu 26.04

Supported by every install route. It used to be container-only, for two
reasons that have both been dealt with:

* **Python.** Resolute packages no `python3.12` at all — not the interpreter,
  not the venv module. The package list now asks for the distribution's own
  `python3`, which is 3.12 on noble and 3.14 on resolute, and `pyproject.toml`
  accepts `>=3.12,<3.15`. Five dependencies needed newer pins to get 3.14
  wheels: `asyncpg`, `PyYAML`, `Pillow`, `pydantic` and `SQLAlchemy`.
* **Guacamole.** Ubuntu stopped packaging `guacd` after noble, so Labtris
  builds it from the Apache release tarball — see
  [Building guacd](/reference/building-guacd). The installer uses the
  archive's copy where there is one and the built package where there is not.

**One thing does not work on 26.04: the RDP console.** Guacamole 1.6.0 does
not compile against FreeRDP 3, which is the only FreeRDP resolute ships, so a
26.04 machine gets VNC, SSH and telnet consoles and no RDP. QEMU consoles are
VNC, so this only affects connecting to a Windows guest over RDP. If you need
that today, use 24.04 or the container install, which pulls
`guacamole/guacd` as a prebuilt image with RDP in it.

The unit suite runs identically on both: 332 passed, 1 skipped, and the same
10 pre-existing environment-dependent failures on 3.12 and 3.14 alike.

## Already running Labtris?

```
curl -fsSL https://labtris.com/upgrade | sudo bash
```

Goes to the latest release rather than tracking `main`, dumps the database
before it migrates anything, and reports whether the result is serving. Labs,
pods, images and the database carry across. `--check` says what it would do
and changes nothing; see [Upgrading](/install/guide#upgrade) for the order of
operations and the rollback it prints on failure.

Coming from EVE-NG instead? [Migrating from EVE-NG](/migrate-from-eveng).

## One line, on a fresh Ubuntu 24.04 or 26.04 machine

```
$ curl -fsSL https://labtris.com/install | sudo bash
```

The script installs every dependency, clones the repo to `/opt/labtris`,
sets up Postgres, the service user, the systemd units, and the reverse
proxy, and finishes with a summary block naming the URL to open, the
config file, and where the generated database password lives. It is
idempotent — re-run it to upgrade, or after a failed install; nothing
gets rotated that does not need to.

The whole thing takes about five minutes on a machine with a route out.
Nothing about the install is secret to the script — it is
`packaging/install-labtris.sh` in this repo, invoked by
`get.sh`, and you can read both before running either.

## With Docker, on any Linux host

If the machine already runs Docker and has working KVM, this is the
shortest path and the easiest to upgrade — a tag bump rather than a
reinstall.

```
$ curl -fsSL https://raw.githubusercontent.com/labtris/labtris/main/docker-compose.yml \
    | docker compose -f - up -d
```

That is the whole install — the image is public, so there is nothing to
clone and no registry login. Clone the repo instead if you want to
sideload your own images or run the end-to-end check.

Every Labtris process shares one private container namespace, so the lab
bridges, taps and nftables rules land there rather than on the machine's
own network stack — `ip link` on the host stays exactly as you left it.

Two things it will not do, both because of that isolation: `cloud`
networks, which put a lab on a physical segment by enslaving a real NIC,
and the management-network settings that rewrite the host's netplan. Both
answer with an explanation rather than failing obscurely. It also needs
`/dev/kvm` and refuses to start without it, rather than falling back to
software emulation at a speed nobody wants.

Docker Desktop on macOS and Windows is not a supported path — there is no
`/dev/kvm` to give it. Run a Linux VM instead.

Full detail, including how to get images in and what each container is for,
is in [Install with Docker](/reference/docker).

## From the ISO

For a machine with no route out, or when the whole point is bare-metal
provisioning. One image carries every Debian package, every Python wheel
and the built interface. Nothing is fetched while it installs.

Grab it from the [latest release](https://github.com/labtris/labtris/releases/latest).
The image is ~3.2 GB, over GitHub's 2 GiB per-asset cap, so it is attached
in two parts (`labtris-<version>-amd64.iso.part-00` and `part-01`) with a
`sha256` checksum of the finished ISO alongside. Join and verify:

```
$ cat labtris-0.13.9-amd64.iso.part-* > labtris-0.13.9-amd64.iso
$ sha256sum -c labtris-0.13.9-amd64.sha256
```

The joined file has to keep the versioned name — that is what the `.sha256`
names inside it, and `sha256sum -c` checks that filename rather than whatever
you piped into.

Then **attach the `.iso` to a VM and boot it** — Proxmox, ESXi, VMware,
Hyper-V, VirtualBox or QEMU. 6+ vCPU, 12 GB RAM, 60 GB of disk, and nested
virtualisation on if you want QEMU nodes inside it to run at useful speed.

For bare metal, write the image to a USB stick with
[Etcher](https://etcher.balena.io/) or [Rufus](https://rufus.ie/) — both have
a device picker, so there is no chance of naming the wrong disk.

The checksum is of the *finished* image, so it verifies the join as well
as the download — do not skip it, a truncated part produces an ISO that
boots and then fails partway through the install.

Boot the machine from it. The install is unattended and takes six to ten
minutes; most of that is the package set being unpacked from the disc.

When it finishes, the console shows the address it is serving on. Open
`https://<that address>` — port 443, with a self-signed certificate, so the
browser warns once. Plain `http://<that address>` redirects there.

`http://<that address>:8081` also works and is plain HTTP, which is the easier
one to use through an `ssh -L` tunnel where a certificate for the real address
would not match `127.0.0.1` anyway. Both ports reach the same instance.

## If the disk looks half its size

Images installed before 0.13.10 used Ubuntu's default LVM sizing, which gives
the root logical volume roughly **half** the disk and leaves the rest
unallocated. A 60 GB disk ends up with a 29 GB filesystem, and a Labtris host
storing qcow2 base images and per-node overlays runs out of room while `vgs`
still reports free space — a confusing way to fail.

Check with:

```
$ df -h /
$ sudo vgs                 # VFree is what is sitting unused
```

If `VFree` is not zero, hand it to the root volume. This is safe online — ext4
grows while mounted, and nothing has to be unmounted or rebooted:

```
$ sudo lvextend -l +100%FREE /dev/ubuntu-vg/ubuntu-lv
$ sudo resize2fs /dev/ubuntu-vg/ubuntu-lv
$ df -h /
```

<Note>
Those are the names Ubuntu's installer uses. Confirm yours first with
`sudo lvs` — the volume group is `ubuntu-vg` and the volume `ubuntu-lv` on a
stock install, but not if you partitioned by hand. If the filesystem is XFS
rather than ext4, the second command is `sudo xfs_growfs /`.
</Note>

New ISOs from 0.13.10 set `sizing-policy: all`, so the whole volume group goes
to the root volume at install time and there is nothing to do.

> **The machine's own login** is `labtris-admin` / `labtris`, and it forces a
> change on first use. That is the *operating system* account, for shell access.
> It is not the Labtris account — see [Users and access](/users).

### Trying it without a machine

The same ISO boots under QEMU, and touches no disk of yours:

```
$ ./packaging/iso/test-boot.sh dist/labtris-*-amd64.iso
```

It prints a serial console address, a VNC address, and forwards the web
interface to a port on the host.

### Installing with no network attached

This is supported and tested — the installer has been run on a VM with no
network interface at all. The installed system writes a DHCP configuration for
any ethernet it may later be given, so you can install offline and connect the
machine afterwards.

## From source

For development, or to run it somewhere the ISO does not suit.

```
$ python3 -m venv .venv && . .venv/bin/activate
$ pip install -e '.[dev]'

$ make dev-db        # Postgres in Docker
$ sudo make netd     # the privileged network daemon — needs root
$ make api           # http://localhost:8080
$ make web           # the interface, on http://localhost:5173
$ make guacd         # optional, for VNC and RDP consoles
```

Two of those deserve explanation.

**`sudo make netd`** runs the only component that needs root. Every operation
that touches netlink or nftables — creating a bridge, moving an interface into a
container, setting up NAT — goes through it over a Unix socket. The API itself
runs unprivileged and cannot reach the kernel directly. That split is why the
web-facing process being compromised is not the same as the host being
compromised.

**`make web`** runs a dev server with hot reload. To serve the interface from
the API instead — which is what a real install does — run `make web-build`
first. `web/dist` is gitignored, so it needs rebuilding after any UI change.

### If a port is taken

Postgres is the usual collision. Set a different one before `make dev-db`:

```
$ export LABTRIS_PG_PORT=55432
$ export LABTRIS_DATABASE_URL=postgresql+asyncpg://pnl:pnl@localhost:55432/pnl
```

## Building the ISO yourself

```
$ ./packaging/iso/build.sh
```

It resolves the package closure with debootstrap, downloads the wheels, builds
the interface, and writes `dist/labtris-<version>-amd64.iso`. It takes 20–30
minutes and needs about 12 GB free. See [Running the
server](/operations#building-the-installer) for what goes on the disc.
