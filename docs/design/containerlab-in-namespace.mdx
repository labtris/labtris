---
title: "Spike: running containerlab inside Labtris"
description: "Whether containerlab's netlink wiring lands in Labtris's namespace when the CLI runs inside the pod. It does."
---

## The question

"Run your containerlab CLI and see the devices in the Labtris UI" sounds
like a Docker API shim: expose a Docker-compatible endpoint, let the user
point `DOCKER_HOST` at Labtris, and intercept the container calls.

That does not work, and the reason is worth stating plainly.
**containerlab does not do its wiring through Docker.** It uses the Docker
API to create containers, then builds veth pairs and moves them into
network namespaces over netlink, as the process running on that host. A
shim would get you the nodes and none of the links.

So the design question was narrower: if containerlab runs *inside* the
pod — joined to the same network namespace netd owns, pointed at the same
dockerd that runs container nodes — does its netlink wiring land where
Labtris can see it?

## Result: yes

Run against a live instance, 2026-09-26. containerlab 0.79.0, two
`linux`-kind alpine nodes, one point-to-point link:

```
docker run --rm --privileged \
  --network container:<labnet> --pid container:<labnet> \
  -v <project>_dind-sock:/dockersock \
  -e DOCKER_HOST=unix:///dockersock/docker.sock \
  ghcr.io/srl-labs/clab:latest containerlab deploy -t spike.clab.yml
```

```
INFO Creating container name=n2
INFO Creating container name=n1
INFO Created link: n1:eth1 ▪┄┄▪ n2:eth1
```

The link is real, not just reported. Addresses on each `eth1`, then:

```
2 packets transmitted, 2 packets received, 0% packet loss
round-trip min/avg/max = 0.116/0.119/0.123 ms
```

The containers land on Labtris's own dind — the same daemon that runs
container nodes — and the veths land in labnet's namespace, visible from
netd.

## Reconciliation

`POST /labs/import/topology` takes `adopt_clab: "<name from the .clab.yml>"`.
It builds the lab from the topology the ordinary way, then binds each node
to the container containerlab already started — `clab-<lab>-<node>` on the
same dockerd — setting `runtime_ref` and `state=running` rather than
starting anything.

Measured on a live instance:

```
"adopted": { "adopted": ["n1", "n2"], "missing": [], "clab_lab": "spike" }

nodes:
  n1 running ref=c9569c31605c
  n2 running ref=d105521c2f8a
links: 1
```

The canvas draws it like any other lab, and `console/exec` on an adopted
node returns `n1` — Labtris is executing inside containerlab's container,
so the binding is live rather than cosmetic.

A node in the file that clab did not deploy is left in `defined` and named
in a warning. A topology can legitimately describe more than was brought
up, and a half-adopted lab is still worth having.

## Two things the spike turned up

**Interface names do not match Labtris's naming gate.** containerlab
creates `vethc9f7a85` and `br-3f03464b7aff`; `IFNAME_RE` accepts neither.
That gate is what stops netd deleting `docker0` or a host NIC, so it
should not be loosened. Either the reconciler records clab-owned devices
as unmanaged, or the integration asks containerlab to name them — the
first is safer.

**containerlab hits the same read-only sysfs wall netd does:**

```
WARN failed to enable LLDP on docker bridge:
     open /sys/class/net/br-.../bridge/group_fwd_mask: read-only file system
```

It warns and carries on, so LLDP is silently not enabled on its
management bridge. Independent corroboration that a container joining
another container's network namespace gets `/sys` mounted read-only no
matter how privileged it is — and a reminder that the fix netd uses
(`IPRoute.brport()` over netlink) is the one that works here.

## What shipped instead of the recommendation

The spike recommended a `labtris clab deploy` wrapper, on the reasoning
that Labtris has to be the one invoking containerlab in order to know a
deploy happened. That reasoning was wrong, and the wrapper was not built.

Labtris does not need to invoke containerlab to know about it, because
containerlab labels every container it creates — `containerlab=<lab>`,
`clab-node-name`, `clab-topo-file` — and the Docker daemon publishes
container events. Watching that stream gets the same information with none
of the wrapping, so the user runs the real CLI, unwrapped, and the lab
appears. `labtris_api/clab_watch.py`, and
[the containerlab reference](/reference/containerlab) for the user-facing
version.

An eBPF trace of `execve` was also considered and rejected: it would have
to reconstruct from argv what the labels already state, and it would still
miss a deploy that happened while the API was down, which a sweep at
startup does not.

### The wiring survives without the topology file

The one thing the spike did not anticipate. `clab-topo-file` points at
`/work/spike.clab.yml` — a path inside the throwaway container the deploy
ran in, which the API cannot read. Verified on the instance:

```
$ docker exec ...-api-1 ls -l /work/
ls: cannot access '/work/': No such file or directory
```

The links are recoverable anyway, because each veth end reports its peer's
ifindex. Reading both node namespaces through the new `netns.links` verb:

```
n1: eth1 ifindex=9  peer_index=10
n2: eth1 ifindex=10 peer_index=9     -> one link
n1: eth0 ifindex=7  peer_index=8     -> peer is on the mgmt bridge, not a node
```

Two interfaces in different namespaces that name each other are the two
ends of one cable; `eth0` never pairs, so clab's management network stays
out of the topology without being special-cased.

Measured against a three-node triangle, with the topology file
deliberately unreachable:

```
clab:    a:eth1 ▪┄┄▪ b:eth1    b:eth2 ▪┄┄▪ c:eth1    c:eth2 ▪┄┄▪ a:eth2
labtris: a eth1 <-> b eth1     b eth2 <-> c eth1     a eth2 <-> c eth2
```

All three, from the dataplane alone. `console/exec` on node `b` returns `b`
and shows `eth2@if35` up at MTU 9500, so the binding is live.

This makes the dataplane the better source in one respect: it reports what
is running rather than what was requested. It is the worse source in
another — kinds, startup config and labels exist only in the file — so the
file is preferred when readable and the lab carries a warning when it is
not.
