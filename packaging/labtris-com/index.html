The LLM-native network lab.

Draw a topology in your browser. It boots as real Docker containers and QEMU virtual machines, wired together with the kernel's own networking. Every operation the UI does, the REST API does; every REST endpoint has an MCP tool. A Claude Code or Cursor session drives your lab the way it edits a file — with real consoles, real packet capture, and hot snapshots that carry running state between hosts.

$ curl -fsSL https://labtris.com/install | sudo bash

Fresh Ubuntu 24.04 host, roughly ten minutes end to end. Refuses to run on anything it hasn't been tested on — set LABTRIS_FORCE_OS=1 to skip the check. Prefer bare metal? Grab the ISO.

Why this exists

LLMs now generate networking software faster than the labs that used to test it can keep up. The mature options — GNS3, EVE-NG, PNETLab, containerlab — were designed for a person clicking, not for an assistant iterating. Fighting a click-only UI to make a model verify what it just wrote is where the reason for this project started.

I did not set out to build a lab tool. I set out to develop new networking features on my own infrastructure — test their compatibility across guests, debug the configurations that came out, reproduce the issues customers were seeing — and, the piece that pulled everything together, fine-tune LLM models on the specific task of reading a running network and telling me what was wrong with it.

None of the tools listed further down let me point an AI assistant at a live topology and iterate. So the MCP surface, the VNC tools that make a graphical guest first-class for the model, the hot snapshots that hand a broken state to someone else in a file — those are here because I needed them for my own work. Turned out other people wanted the same shape.

What it is

An interactive network topology tool. You draw nodes on a canvas, connect them with links, and the guests come up as real Docker containers or QEMU virtual machines with the wiring you drew. Consoles, packet capture, VLANs, NAT, VXLAN across hosts, netem link impairment — the parts a network person expects to be there.

It is the shape of EVE-NG and GNS3 without either's baggage. One process, one Postgres, no license file, no cloud sign-in. You install it on your own machine and you own the result.

Three things that make it different

01The container console is a real terminal.

Not a form field that submits a command. A PTY, so cd persists, Ctrl-C interrupts, top redraws, an ssh into a lab node behaves like an ssh. Bash writes its prompt to stderr and the container wrapper used to swallow it — that was fixed in 0.5.0, and the reason we tell you is that "the container prompt looked blank for a week" is the level of care this thing gets when something small breaks.

02Snapshots of a running lab, portable to another host.

labtris lab snapshot <id> --mode hot writes the entire lab into a .tar.gz — topology, per-node disks, live QEMU memory, and committed container filesystems. labtris lab load <path> on any other Labtris host restores it as a new lab that resumes at the exact moment you captured. Modelled on LocalStack pods. Verified round-trip: write a marker file inside a running container, snapshot, load, start — the marker is still there.

03An AI-assistant surface designed for real work, and for training on it.

The MCP tools expose VNC screenshots (with an OCR shortcut so reading a login prompt costs 15 tokens instead of 1500), typed keys with sendkey combos, and pixel-accurate mouse clicks via QMP. Every operation the UI does, the API does; every API endpoint has an MCP tool wrapper. So a Claude Code or Cursor session can install Ubuntu Desktop, walk a vendor appliance wizard, or debug a broken BGP session the same way it edits a config file. If you are using an AI assistant for actual troubleshooting — or training one on your own infrastructure — it needs a place to try things and see what happens. That is what this is.

Why not just use…

The honest question. There is no shortage of network lab tools, and a few of them are excellent. Here is where Labtris fits, in the voice of someone who has used all of these on real projects.

…GNS3

The closest match, and the most mature open-source option — bigger vendor coverage, a bigger community, an installer that has been polished for over a decade. If you already have your image library set up and you are happy driving a desktop client, keep using it. Labtris is a bet on three things GNS3 does not lead with: a browser-only interface (no local install for a user, one server for a class), a first-class AI-assistant surface (MCP tools plus a chat panel that streams what the model is doing), and hot lab snapshots that resume exactly where you captured. If those matter, try Labtris. If they do not, GNS3 is a fine answer.

…EVE-NG or PNETLab

EVE-NG Community is free but not open source; the Pro tier is what most people who need the extra features end up on. PNETLab is free and closed-source. Both were the shape Labtris borrowed from — the canvas, the palette, the folders, the config sets, the console tabs. What Labtris changes is the licence (MIT), the trust model (the source is here, in this repo, no phone-home) and the upgrade story (git pull && systemctl restart, no licence file, no bootstrap script that connects to a remote server you cannot see). If open source is a hard requirement — for a university, a public-sector lab, a homelab you want to still work in five years — this is why Labtris exists.

…containerlab

Containerlab is excellent for what it does well: declarative YAML topologies, CLI-first workflow, easy to put in CI. If your lab is all containers and you like infrastructure as code, use it.

The reason Labtris was not built on top of it is QEMU. Containerlab supports vendor VMs by wrapping them in Docker images via vrnetlab — an IOSv qcow2 becomes a Docker image with QEMU inside it, and the "container" you run is really a container-around-a-VM. That works, but it is a workaround for a shape mismatch: QEMU is not a container, does not benefit from container isolation (it runs as root with /dev/kvm access anyway), and the double layer of indirection means the QEMU stderr you actually want to read when a VM will not boot is hidden inside a container abstraction that adds nothing.

With modern LLM-assisted development, writing a native QEMU runtime alongside a Docker one is a weeks-of-work project, not a years-of-work one. Labtris did it: QEMU processes are supervised directly, disk overlays sit on the host filesystem, HMP and QMP sockets are per-VM, and the same process orchestrates Docker containers on the same canvas. If you are picking between "wrap every vendor VM in a container-around-a-VM" and "just run the VM," pick the second. It also has a UI, which containerlab does not.

…Cisco CML / VIRL

Commercial, licensed per user, Cisco-focused. If your team is all-Cisco and the license is paid for, it is the smoothest experience for Cisco images specifically. Labtris is vendor-neutral — any container, any qcow2 — and does not need someone in procurement.

…vrnetlab or netlab

Complementary rather than alternative. vrnetlab is the QEMU-VM- as-Docker-container wrapper containerlab leans on; you can bring a vrnetlab-built image to Labtris just as easily as anywhere else. netlab is a topology-generator and Ansible-config-pusher that sits on top of containerlab; a similar layer over Labtris is on the list. If you already use either, keep using them — Labtris does not replace them.

What isn't built yet

Configuration generation. Labtris draws the links; it does not write addresses or bring up OSPF and BGP for you. Ready hooks can tell you when addressing has converged; they will not do the addressing.

A vendor node catalogue. Docker and QEMU run whatever image you bring, and the bootstrap runner is the framework for one, but the list of vendors with recipes today is small.

Classroom features. Shared labs, cohorts, per-user quotas, lab instructions — designed, unbuilt. Ownership and lock exist; the class layer on top does not.
